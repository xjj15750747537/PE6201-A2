# D2(b) verification — mean tokens per tool call, v1 vs v2 (gpt-4o-mini)

Generated by `verify_d2b_v1v2_tokens.py`. Raw per-trial output: `d2b_v1v2_raw_trials.csv`.
Machine-readable summary: `d2b_v1v2_summary.json`. Source data: `results/d2b_v1v2_source/` —
the two measured live-battery run files this table is computed from, committed as-is.

This is an archived descriptor-only table from an earlier interface revision. It must not
be presented as the final D2(b) live comparison, because the submitted v1/v2 experiment
now also changes the concrete `get_clinic_slots` return shape. A final live comparison must
run both current versions on the same model and 93-trial set after that change.

The historical script was intended to recompute a table that was already circulating (as a
Word table) directly from two real measured gpt-4o-mini live-battery runs, instead of
restating hand-typed numbers.
Both source files are real live runs (`token_usage_kind: provider_reported`), not scripted
estimates — `tokens_in` / `tokens_out` on every trial come from the model provider, and
`evidence` is the ordered list of tool calls the live model actually made in that trial.

**Comparability, checked automatically by the script:** same model
(`openai/gpt-4o-mini`), same 93-trial set, same `prompt_contract_revision`
(`json-contract-2026-09-16-tool-protocol`) for both v1 and v2. The script
stops with an error if any of these three ever stop matching.

**What "per call" means here, and what it does not mean:** the provider
reports ONE usage figure per model response/trial — it does not break
usage down per individual tool call inside a multi-call trial. "Mean
tokens per call" below is that trial total divided evenly by the trial's
tool-call count, then aggregated over all 93 trials — a clearly-labelled
derived average, **not** provider-measured per-individual-tool-call
attribution. Report it as "on average, each tool call corresponded to
about this many tokens," not as "we measured what each tool call cost."

| Mean output tokens per call | 70.3 | 53.9 | −23.3% |
| Total tool calls (93 trials) | 236 | 279 | +18.2% |
| Trials | 93 | 93 | — |
| Pass rate (this run) | 88.2% (82/93) | 87.1% (81/93) | −1.1pp |

already a percentage — see `change.pass_rate_pp` / `change.total_tool_calls_pct` in the
summary JSON.

Matches the previously-circulated table exactly (1,824 / 2,240 / 70 / 54 / 236 / 279, rounded
to whole numbers there). This script is the first committed, reproducible source for those
numbers.

## Breakdown: turns, and pass rate by case type

| | v1 | v2 |
|---|---:|---:|
| Mean turns per run | 2.47 | 2.76 |
| Positive-case pass rate (36 trials) | 35/36 (97.2%) | 35/36 (97.2%) |
| Negative-case pass rate (57 trials) | 47/57 (82.5%) | 46/57 (80.7%) |

"Turns" is the record's own `turns` field (a live model turn), not the `tool_calls`/`evidence`
count — a turn can bundle more than one tool call, so the two numbers differ (e.g. v1: 236
total tool calls over 230 total turns). "Negative case" uses the same rule `harness.py` uses
to set trial counts (`harness._is_negative`: correct outcome is `ask` or `escalate`, not
`act`). The pass-rate movement between v1 and v2 is driven entirely by negative cases;
positive-case pass rate is unchanged.

The historical v1→v2 rewrite changed every descriptor field (purpose, when-to-call,
arguments, returns, failure guidance) from generic wording to domain-specific instructions
on **all six** Problem B tools. The final submitted implementation additionally changes the
concrete `get_clinic_slots` payload: v1 returns a broad dictionary with all matching slots,
while v2 returns a compact list of free slots. Therefore, do not mix this archived
descriptor-only live result with the final return-shape implementation.

## Open item, not resolved by this script

`nicole-gpt4omini-v1-protocolfix-01.json`'s **filename** says "v1" (it is named after the
protocol-fix batch it belongs to), but the `prompt_version` field **inside** the file is
`"v2"` — it is in fact the v2 run. `verify_d2b_v1v2_tokens.py` reads the field inside the
file, not the filename, and refuses to run if the field doesn't match what it expects, so
this table cannot silently regress if someone renames the file later. Flagging this so
nobody "corrects" the file by swapping it for an actual second v1 run based on the name
alone — the content is already the v2 measurement the table needs.
